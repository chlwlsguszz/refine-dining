아키텍처 구조도

사용자 요청이 흐르는 서비스와, 근거 자료를 만드는 사전 처리를 나누어 볼 수 있습니다.

현재 로컬 데모는 Spring Boot가 화면과 API를 제공하고 H2를 사용합니다. MySQL은 별도 실행 구성입니다.

작은 화면에서는 그림을 좌우로 스크롤할 수 있습니다.

  • 중량 검색용 E5는 요청마다 호출하는 로컬 서비스이고, 식품 매칭용 E5는 사전 처리에서 실행합니다.
  • 중량의 수율·출처는 JSON에서 읽습니다. 173건의 검색 벡터는 Python 메모리에 보관합니다.
  • Qwen의 매칭 판정은 별도 실험 기록이며, 실제 비교 관계는 관리자가 검수합니다.
  • 검수한 RAG 관계를 기존 food_materials에 자동 반영하는 연결은 아직 없습니다.

데이터 정제와 RAG 매칭

실험 기준을 고정하고, 검색으로 후보를 좁힌 뒤 원문과 근거를 대조합니다.

이 흐름은 Python 배치로 실행합니다. 제안이 만들어져도 검수 전에는 비교 관계를 확정하지 않습니다.

  1. 수집·정제에서 빠지는 이유 집계

    식품명·분류 누락, 생것 부모 없음, 미등록 조리 코드 등의 사유를 행별로 하나씩 부여합니다. 조회 API는 원본 DB에 적재된 행을 기준으로 동작합니다.

    GET /api/admin/food-data/refine-report

  2. 원본 스냅샷과 실험 분할 고정

    3,701행을 고정했습니다. 같은 소분류에 생것이 없고 상위 분류에 생것이 있는 109행을 47개 식품군으로 묶어 개발 77행·최종 평가 32행으로 나눴습니다. 같은 식품군은 한쪽에만 배정했습니다.

    raw-snapshot.json · review/split-manifest.json · 초기 검수 20행은 개발 77행에 포함

  3. 생것 2,388행을 로컬 벡터로 변환

    multilingual-e5-small ONNX로 식품명을 384차원 벡터로 변환합니다. NumPy 배열과 .npz 파일로 저장·검색합니다. 별도 벡터 DB는 사용하지 않습니다.

    embed_food_names.py · e5-small-vectors.npz

  4. 검색 후보 5개 구성

    같은 대표식품에서 최대 3개를 E5 순위로 확보하고, 전체 생것 검색에서 나머지를 채웁니다. BM25·E5·RRF 비교 실험 후 현재 정책은 이 E5 기반 검색으로 고정했습니다.

    retrieval_policy.py · family3_global

  5. 공식 문단 검색과 원문 대조

    공식 문단은 적용 범위와 어휘 겹침으로 검색합니다. 식품 후보의 품목·부위·품종·원산지·100g/100mL 기준 등을 대조합니다. 문단 검색에는 현재 벡터를 사용하지 않습니다.

    grounded_rag.py · evidence/passages.json

  6. 근거 제안과 로컬 LLM 판정을 각각 기록

    원문·공식 문단 대조 경로가 검수 제안을 만들고, Qwen3-8B는 같은 후보와 근거로 별도 판정을 생성합니다. 후보 코드, 인용, 충돌 여부를 검증합니다. 개발 자료에서는 제안 3건·보류 74건, Qwen 판정은 77건 모두 보류였습니다.

    run_local_rag.py · local-rag/development.json

  7. 검수 후 비교에 사용

    관리자가 원문·차이·근거를 보고 승인하거나 보류합니다. 자료와 제안 버전이 바뀌면 이전 승인을 그대로 적용하지 않습니다.

    /nutrition/review · rag_proposal · rag_review
판정 용어화면에서 뜻하는 것
직접 비교정해 둔 품목·부위·분류·기준량·관측 조건이 맞는 후보. 동일 시료의 전후 실험임을 보장하지는 않습니다.
참고 비교대응 근거는 있지만 산지·품종·관측 조건 등의 차이나 미확인 사항을 함께 표시할 후보입니다.
보류충돌하거나 근거가 부족해 현재 자료로는 짝을 정하지 않는 상태입니다.

여기서 개발 77행은 초기에 조사했던 수산물 중심 77건과 다른 집합입니다.

영양 질의응답

질문이 들어오면 준비된 카탈로그와 검수 상태를 조회하고, 원자료에 있는 수치로 계산합니다.

생것 후보 검색과 LLM 매칭을 매번 다시 실행하지 않습니다.

  1. 공식 원자료와 스냅샷 대조

    공식 다운로드 3,704행과 스냅샷 식품을 대조했습니다. 3,701행 × 24개 영양 항목에서 관측값 63,125칸, 결측 25,699칸을 구분했습니다. 실제 0인 11,048칸은 결측과 별도로 유지합니다.

    prepare_rag_catalog.py → catalog.json → rag_food

  2. 질문에서 식품·영양소·중량 확인

    Spring이 질문을 해석하고 카탈로그에서 코드·이름·검색어로 식품을 조회합니다. 여러 식품이 걸리거나 단위가 부족하면 선택·추가 입력을 요청합니다.

    POST /api/nutrition/answers · NutritionAnswers

  3. 원문과 승인 상태 확인

    단일 식품의 영양값은 원문에서 제공합니다. 비교는 현재 버전의 승인된 관계를 확인하고, 미승인·보류 관계에는 비교 차이를 제공하지 않습니다.

    NutritionCatalog · NutritionReviews

  4. 서버에서 수치 계산

    기준량과 사용 중량을 적용해 BigDecimal로 계산합니다. 결측값은 0으로 대체하지 않고, 100g과 100mL를 근거 없이 서로 환산하지 않습니다.

  5. 원문·출처·검수 이유와 함께 응답

    필요한 경우 로컬 Qwen이 승인 근거의 허용 문장 ID를 선택합니다. 이 설명 기능은 옵션이며, 수치와 차이는 서버가 계산합니다.

    NutritionExplanation · GET /api/nutrition/foods/{code}

자료를 준비할 때

  1. USDA 원본 실험 기록 정리

    육류·가금류의 조건별 기록 173개를 변환합니다. 173종의 식품이라는 뜻은 아닙니다. 평균·최소·최대 수율, 표본 수, 영어 원문과 셀 위치를 보존하고 검색용 한국어 별칭과 조건 메타데이터를 붙입니다.

    원본 XLSX → import_usda.py → cooking-yields.json

  2. 검색 서버 시작 시 벡터 생성

    한국어 이름·별칭·영어 원문·조리법을 묶어 로컬 multilingual-e5-small ONNX로 384차원 벡터를 만듭니다. 벡터는 Python 메모리의 NumPy 배열에 둡니다. 중량 검색에는 별도 벡터 DB나 영속 .npz 인덱스를 쓰지 않습니다.

    suggest_names.py · passage 접두어 · 평균 풀링 · L2 정규화

사용자가 검색할 때

  1. 식품명과 조리법 입력

    예: 소고기 안심 / 구이 / 200g. 검색에는 식품명과 조리법을 보내고, 중량은 나중의 계산에 사용합니다.

    React /weight → Spring POST /api/weight/search

  2. 의미와 명시된 조건으로 후보 검색

    같은 모델로 검색어를 벡터화해 코사인 유사도를 계산합니다. 동물 종류를 명시하면 범위를 좁히고 부위·조리법 일치를 순위에 반영합니다. 등록된 정확 명칭을 보존해 최대 12개 후보를 반환합니다.

    Spring → Python :18086/search · 최근 128개 질의 메모리 캐시

  3. 차이와 계산 가능 여부 검사

    Java가 동물 종류·부위·껍질·뼈·지방 구간·형태·조리법을 대조합니다. 명시적 충돌이나 필요한 조건을 확인할 수 없는 경우 계산을 막습니다. 생략한 부위·조리법 등은 원문을 확인하도록 안내할 수 있습니다.

    YieldQueryConditions · 이유 / 차이 / canEstimate

  4. 원문을 보고 실험 선택

    사용자가 원문, 손질 상태, 수율, 출처를 보고 적용할 기록을 선택하고 조건을 확인합니다. 선택 전에는 중량을 계산하지 않습니다.

    YieldSearchResults · evidenceId + confirmReference

  5. 선택 재검증 후 수율 계산

    현재 검색 결과에 포함되고 계산 가능한 기록인지 다시 확인합니다. 조리 전 g × 평균 수율(%) ÷ 100을 BigDecimal로 계산해 소수 첫째 자리까지 제공합니다.

    POST /api/weight/predict → REFERENCE_YIELD
실제 수율을 적용한 예시

소고기 안심 200g

‘소고기 안심 / 구이’로 검색한 뒤 ‘소고기 안심 (뼈 제거) / 오븐구이’ 기록을 선택했다고 가정합니다.

200g × 82% = 164g

선택한 원표의 평균 수율을 적용한 참고 중량입니다. 원문은 “Beef, loin, tenderloin roast, boneless…”이며 조리법은 “Roasted”입니다. 이 행에는 최소·최대 수율이 없어 범위를 만들어 표시하지 않습니다.

담당하는 일해석할 때 주의할 점
로컬 E5실측 기록 검색유사도는 확률이나 중량 예측 정확도가 아닙니다. 수율 계산에도 곱하지 않습니다.
Java 조건 검사차이와 계산 가능 여부 판정MATCH 표시도 모든 실험 조건의 동일성을 보장하지 않습니다.
사용자 확인실제 재료와 원문 조건을 비교해 선택선택해도 명시적으로 충돌하는 기록은 서버에서 계산을 막습니다.
Java 수치 계산선택한 실험의 평균 수율 적용온도·시간·품종 차이를 보정하는 별도의 예측 모델은 없습니다.
검색 장애 대체E5 연결 실패 시 NAME 검색이름·부위 기반 검색임을 화면에 표시합니다.
현재 범위는 육류·가금류입니다.

최소·최대 수율이 있는 경우 환산하는 범위는 연구 관측 범위이며, 사용자의 다음 조리에 대한 예측 구간이 아닙니다. 직접 잰 무게는 화면에서 수율을 확인하는 데만 쓰며 학습 데이터로 저장하지 않습니다.
